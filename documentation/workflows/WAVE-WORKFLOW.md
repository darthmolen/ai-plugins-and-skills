# Wave Workflow

A wave runs several plans in parallel. Each plan gets its own track and session, and one lead session coordinates them. Each plan still moves through the `plan-workflow` board as usual. The wave decides when each plan starts, which track owns which files, and when shared contracts freeze. It never rewrites a plan's objective, phases or success criteria.

This page covers when to use a wave and what a person does at each step. The rules the sessions follow are in the [`wave-workflow` skill](../../skills/wave-workflow/SKILL.md).

---

## When to write a wave

Write one when any of these is true:

- more than about four plans are live at once;
- a queued plan is held by something other than its stated dependency;
- two plans want the same track;
- the same file appears in three or more plans' *Files Expected to Change*.

Two or three plans do not need a wave; check `planning/in-progress/` instead. A wave written too early is one more document to keep in sync.

---

## What a wave adds to the board

```
planning/waves/
├── waves-context.md                 # every session reads this first
└── wave-<n>/
    └── wave-<n>_<YYYY-MM-DD>.md     # the wave document

planning/WAVE-README.md                    # generated; exists only while a wave is open
planning/wave-<n>_lead_<YYYY-MM-DD>.md     # the lead's plan
planning/wave-<n>_<track>_<YYYY-MM-DD>.md  # one plan per track
```

- **Plans** stay on the board, named `wave-<n>_<track>_<date>.md`, with `wave: wave-<n>` in their frontmatter.
- **The wave document** holds the deliverable, the integration gate, the contracts with their owners and freeze days, which track owns which files, and the calendar.
- **`WAVE-README.md`** is generated by `plan-doc.cs wave-table --fix` while the wave is open. It lists the start commands and where each plan sits, and it is removed when the wave closes.
- **`waves-context.md`** holds the current wave number, how the team works, and the rules learned from earlier waves. It outlives any one wave.

## Starting the sessions

Name every session so it can be messaged.

| Where | Lead | A track |
|---|---|---|
| Terminal | `claude --agent ai-plugins-and-skills:wave-lead --name wave-<n>-lead` | `claude --agent ai-plugins-and-skills:wave-track --name wave-<n>-<track>`, then `track <track>` |
| VS Code extension tab | `/ai-plugins-and-skills:wave-workflow lead` | `/ai-plugins-and-skills:wave-workflow track <track>` |
| Copilot | invoke `wave-workflow` with `lead` | invoke `wave-workflow` with `track <track>` |

In an editor tab, the plugin's `wave-session-title` hook names the session `wave-<n>-lead` or `wave-<n>-<track>` when the prompt is sent, so there is nothing to rename by hand. It reads the names from the open wave's `planning/WAVE-README.md`, and does nothing for any other prompt. It needs pwsh 7; without it, rename the session by hand. The hook is Claude Code only.

The lead and each track start and end through `session-workflow` ([SESSION-WORKFLOW.md](SESSION-WORKFLOW.md)). Once a session has its worktree, and before it changes anything, it writes its session file: a track with the subject `wave:wave-<n>/<track>` in `commit` mode, and the lead with `wave:wave-<n>/lead` in `lead` mode. Each ends its session at every pause point and stop, and starts a new one when it resumes. A track locks each port, local database or container before it runs it, under a name taken from the resource's address such as `port-5000`, so two tracks, or two waves on one machine, cannot run it at once. The hook starts no session; the instructions in `track.md` and `lead.md` do.

Tracks message only the lead, and the lead messages the tracks. Anything one track needs from another goes through the lead, so the lead knows what changed hands.

## Where people stay in the loop

A person supervises every session, approves its steps, and resumes it after each pause point.

- **The lead** writes no production code. It verifies each track's commit from a clean checkout (fresh worktree, warnings as errors, every test project), then pushes the branch and opens the pull request.
- **A track** works in its own git worktree, edits only the files its plan lists, and stops at its pause point. It never pushes or merges; it sends the lead a verified SHA.
- **High-tier plans** (`plan-tier`) get an adversarial review, recorded with `plan-record-review`, before they start.
- **Work only a person can do**, such as redirect URIs, role assignments, environment approvals and service connections, goes to that person as a checklist before the integration window opens.

## Running a wave

1. **Set up.** Write the wave document from the skill's template, a plan for the lead, and a plan per track. Run `plan-doc.cs wave-table --fix`. Promote every backlog stub a plan absorbs, file a stub for every item the wave defers, and answer the plans' open questions in the wave document.
2. **Admit plans to tracks.** A plan starts when its track is free, its file set is disjoint from every in-progress plan's, its dependencies are met (or it codes against a frozen contract), and, if it is High tier, its review is recorded. `plan-doc.cs validate --path planning` reports track and file-set collisions.
3. **Run.** Tracks work to their pause points. Producer contracts freeze first, and their consumers start once they are frozen. After a freeze, a contract changes only through the lead.
4. **Integrate.** Run the integration window as supervised sittings, one per resource owner (database, identity, CI/CD, configuration), then the gate. Do a read-only check before every write, keep a rollback table, and generate secrets inside the command that uses them.
5. **Close.** Tick each integration-gate item with its evidence, close the lead's documents, update the system spec with what shipped, set the wave document to `status: done` and run `plan-doc.cs wave-table --fix`. Record the rules learned in `waves-context.md`, and file what the next wave inherits as backlog stubs.
